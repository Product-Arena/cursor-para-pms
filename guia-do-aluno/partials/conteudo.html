Antes de começar os blocos práticos

Alinhar como usar o Cursor no curso: co-piloto ativo, não delegação passiva — e caminho para ir além do PM tradicional e se tornar builder.

1. Filosofia do curso

Este curso parte de uma convicção simples: o Cursor é um co-piloto, não um substituto. A IA acelera raciocínio, rascunho e execução — mas você mantém o julgamento, o contexto de negócio e a decisão final. Quando tudo vira “manda fazer e espera o resultado”, o aprendizado some e o risco sobe.

Por isso, ao longo do dia, você vai pensar junto com a ferramenta: formular o problema, revisar o plano, validar saídas, corrigir rumo. O agente propõe; você direciona. Esse é o hábito que diferencia quem usa IA de forma profissional de quem só automatiza cliques.

O segundo eixo é ir além do básico de PM. Você já sabe priorizar, escrever requisitos e alinhar stakeholders. Aqui, o próximo passo é construir: montar análises, protótipos, documentos e fluxos com suas próprias mãos (e com o Cursor), sem depender de fila de engenharia para cada experimento. O PM builder entrega mais rápido, aprende mais rápido e conversa com tecnologia em pé de igualdade.

Na prática: em cada exercício, pergunte “o que eu preciso validar antes de aceitar?” — não “o que posso delegar sem olhar?”.

2. Para quem o curso é recomendado

O curso foi desenhado para PMs, builders e pessoas não desenvolvedoras que querem usar o Cursor com intenção — não só “testar IA”. Você não precisa saber programar para acompanhar; precisa estar disposto a experimentar, revisar e iterar com a ferramenta.

Na prática, há três níveis de uso. Todos são bem-vindos; o ganho aumenta conforme você se aproxima do terceiro:

⚡

Rotina e produtividade

Automatizar tarefas do dia a dia: organizar arquivos, rascunhar e-mails, resumir reuniões, pequenos scripts e fluxos repetitivos sem depender de fila técnica.

📊

Conhecimento e entregáveis

Criar documentos, gerar análises a partir de dados, montar narrativas e protótipos rápidos para validar ideias antes de escalar com engenharia.

🛠️

Builder

O maior retorno: entender o que o agente está fazendo, ler e ajustar código com confiança, e construir de ponta a ponta (análise → PRD → protótipo → publicação). É aqui que o Cursor deixa de ser “assistente de texto” e vira ambiente de trabalho.

3. O que é Cursor

Cursor é um ambiente de desenvolvimento integrado (IDE) com IA nativa — pensado para quem trabalha dentro de um projeto: arquivos, pastas, terminal, Git e agentes no mesmo lugar. Não é “um chat que às vezes gera código”; é o lugar onde você edita, executa, revisa e versiona o que está construindo.

Se você já usou VS Code, a interface vai parecer familiar: editor central, explorador de arquivos, terminal embutido e extensões. A diferença é que o chat e os agentes enxergam o seu workspace (o que está na pasta aberta), leem documentos locais (CSVs, PRDs, notas — sem copiar e colar no chat), rodam comandos com sua permissão e propõem mudanças direto nos arquivos — com você aprovando cada passo.

No fim do dia, o Cursor é seu par técnico: rascunha e executa com você — quem decide prioridade, qualidade e “está pronto” é você.

Resumo em uma frase: Cursor = IDE + agentes com contexto do seu workspace. Quanto mais você trata como ambiente de trabalho (e menos como chat solto), mais perto fica de ser builder de verdade.

4. Principais diferenciais da ferramenta

O mercado oferece várias interfaces com IA — chat, geradores visuais, automação e IDEs. O Cursor não substitui todas; ele se destaca quando você precisa trabalhar no seu projeto real: arquivos locais, terminal, Git e entregáveis que evoluem no mesmo repositório (como na seção 3).

Outro diferencial importante: o Cursor é agnóstico de modelo e provedor. Na mesma IDE você escolhe qual LLM usar — por exemplo OpenAI (GPT), Google (Gemini), Anthropic (Claude), DeepSeek e outros conforme disponibilidade nas configurações. Você não fica preso a um único ecossistema; pode trocar de modelo por tarefa (rascunho rápido vs. raciocínio longo) sem mudar de ferramenta.

5. Outros conceitos importantes (glossário)

Vocabulário mínimo para acompanhar o dia — cada item aparece de novo nos blocos práticos.

GitHub

Pense no GitHub como um Google Drive para código: arquivos e pastas na nuvem que você baixa para o PC e mantém sincronizados com o time. Um repositório (repo) é o projeto inteiro — na prática, uma pasta. Clonar (git clone) é copiar/baixar esse repo para a sua máquina (no curso, dentro de repos/).

Quatro palavras que aparecem o tempo todo:

  • Commit — um “salvar” com mensagem: registra um pacote de mudanças no histórico (como uma versão nomeada do arquivo).
  • Push — enviar seus commits locais para o GitHub (subir para a nuvem).
  • Pull — baixar o que o time (ou você em outro PC) já enviou para o GitHub (trazer da nuvem).
  • PR (Pull Request) — pedido de revisão: “quero juntar esta linha de trabalho na principal”. O time comenta, aprova e só então entra no código oficial.

No curso, isso serve para material da aula, versionar entregas e publicar protótipos (ex.: GitHub Pages).

MCPs

MCP = Model Context Protocol: um protocolo (padrão de comunicação) que liga o Cursor a ferramentas externas — Linear, Drive, APIs — sem copiar e colar entre abas. O agente chama o conector; você autoriza o que pode ser lido ou escrito. No curso, instalamos MCPs pelo Cursor Marketplace (detalhes em MCPs, bloco 03).

Agents

Um agente é uma IA configurada para executar tarefas em etapas, não só responder uma mensagem. Em vez de um único texto na tela, ele planeja, usa ferramentas e itera até chegar num resultado. Três peças costumam aparecer em qualquer plataforma:

  • System prompt — instruções fixas de “quem você é” e como deve trabalhar (papel, tom, regras, o que nunca fazer).
  • Tools — capacidades que o agente pode acionar: ler arquivo, buscar na web, abrir issue no Linear, rodar comando, etc. (muitas tools passam por MCPs).
  • Memória — o que o agente guarda entre mensagens ou sessões: preferências suas, decisões do projeto, notas em memory.md ou histórico da conversa, para não recomeçar do zero.

No Cursor, o modo Agent é uma implementação disso no seu workspace; nos blocos práticos você vê isso na prática.

Modelos

Modelo é o LLM por trás do chat — GPT, Claude, Gemini, DeepSeek e outros. Cada um foi treinado com dados e objetivos diferentes, o que o torna melhor em certos tipos de tarefa (e pior em outros). Vale testar e conhecer um pouco o perfil dos principais antes de “travar” um só.

Na prática, a escolha impacta três coisas: custo, latência (velocidade de resposta) e janela de contexto (quanto do seu projeto cabe de uma vez na conversa).

  • Problemas complexos / planejamento — modelos “fortes” e mais lentos: ex. GPT-5.5 (OpenAI) e o análogo Opus (Anthropic). Bons para raciocínio longo, arquitetura, PRD difícil, análise com muitas variáveis.
  • Tarefas simples e rápidas — variantes mini, instant ou intermediárias como Sonnet: mais baratas e rápidas para rascunho, reformular texto, perguntas pontuais, edits pequenos.

No Cursor você troca de modelo nas configurações (seção 4) — use o pesado quando precisar pensar; use o leve quando precisar velocidade.

Markdown

Markdown (.md) é formato de texto simples com títulos, listas e negrito — legível para humanos e para a IA. No curso, PRDs, análises, backlogs e instruções de agente costumam ser Markdown: fácil de editar no Cursor, versionar no Git e publicar (Notion, GitHub, etc.).

Configurando seu workspace

Abra o workspace modelo, deixe a interface no tema claro e ative as proteções do agente — assim o Cursor enxerga seus arquivos com contexto estável e você mantém controle sobre exclusões e comandos no terminal.

Objetivo: Abrir o workspace baixado; tema light; ativar File deletion protection e Allowlist with sandbox antes dos exercícios com Agent.

1. Abrir o workspace modelo baixado

Se ainda não concluiu, faça o roteiro com checkboxes em Pré-requisitos → workspace modelo (baixar, descompactar, File → Open Folder… e validar repos/ + .cursor/).

Pastas na raiz

cursor-workspace/
├── .cursor/          ← rules, commands, templates, skills, workflows
├── repos/            ← repositórios clonados (curso, cases, referências)
├── projects/         ← projetos e protótipos do dia
└── documents/        ← análises, rascunhos e entregáveis em Markdown

A pasta .cursor/ concentra rules, commands e templates — o agente consulta antes de agir. O clone do repositório do curso vai em repos/.

2. Ajustar o tema para light color

Se você preferir utilizar o tema claro, há duas formas de chegar no mesmo resultado — use a que for mais rápida para você:

Opção A — pelo menu Settings

  1. Cursor → Settings (ou Cmd + , no Mac · Ctrl + , no Windows).
  2. Themes → Color Theme.
  3. Selecione Cursor Light (ou outro tema Light da lista).

Opção B — pela Command Palette

  1. Abra a paleta com Cmd + P (Mac) ou Ctrl + P (Windows).
  2. Digite > (símbolo “maior que”) para filtrar comandos.
  3. Escolha Preferences: Color Theme e selecione Cursor Light (ou outro tema Light da lista).

O nome exato do tema pode variar levemente por versão — o importante é um tema Light com bom contraste no editor e no chat.

3. Ativar File deletion protection

O Agent pode propor exclusão de arquivos. Com a proteção ligada, o Cursor não apaga arquivos do workspace sem você aprovar explicitamente.

  1. No menu superior: Cursor → Settings → Cursor Settings.
  2. No campo de busca das configurações, digite file deletion.
  3. Localize File deletion protection e ative o toggle (ligado).

Ative antes de clonar repositórios ou deixar o Agent atuar em pastas com material importante — alinhado ao que veremos em Rules.

4. Habilitar Allowlist with sandbox

No modo Agent, o Cursor pode rodar comandos no terminal. Allowlist (with sandbox) limita o que roda sozinho e isola a execução: o agente propõe, você define o que está liberado e aprova o resto.

Em resumo:

  • Allowlist — só comandos que você aprovou entram na lista (ex.: git, ls, cd). O resto pede permissão.
  • Sandbox — a execução fica mais isolada do resto do sistema, reduzindo surpresas fora do workspace.

Como ativar

  1. Cursor → Settings → Cursor Settings.
  2. No campo de busca, digite allowlist.
  3. Em Auto-run mode, selecione Allowlist (with sandbox).
  4. Revise a lista de comandos permitidos — no curso, o instrutor indica o mínimo para Git e navegação.

Modos de uso (Ask, Plan, Agent e outros)

Os modos definem como você interage com o modelo: conversar, planejar, executar — e há modos complementares (Debug, Multitask) para casos mais pontuais.

Objetivo: Usar Ask e Agent com confiança; saber quando usar Plan; contextualizar allowlist, escolha de modelos e janela de contexto; conhecer Debug e Multitask em nível introdutório.

Ask, Plan e Agent — qual modo usar?

No chat do Cursor você escolhe como a IA participa: só conversar, planejar antes de agir ou executar mudanças no projeto. A regra prática: quanto mais o modo pode alterar arquivos e rodar comandos, mais você deve revisar e aprovar cada passo.

Comparativo com analogia e exemplo

Modo Analogia O que acontece no Cursor Exemplo no curso
Ask Consultar um especialista sem deixá-lo mexer na sua mesa Responde perguntas e lê contexto (@ arquivos, pastas arrastadas). Não edita arquivos nem executa comandos sozinho. “O que o comando fetch faz?” e organizar o chat — seção Ask
Plan Reunião de alinhamento antes da obra começar Monta um plano passo a passo (checklist, comandos sugeridos). Você valida o roteiro; a execução vem depois, com sua aprovação. Clonar um repositório em repos/ pedindo um plano antes de rodar git clone — seção Plan
Agent Colega com acesso ao seu computador — com sua autorização Edita arquivos, propõe diffs e pode rodar o terminal (respeitando a allowlist do Bloco 01). Você revisa cada mudança e comando. Criar notas-da-aula.md com template de notas — seção Agent

Como escolher rápido: dúvida ou entendimento → Ask; tarefa nova com vários passos → Plan; “faça isso no projeto” → Agent (sempre revisando).

Modos complementares

Além dos três acima, o Cursor oferece modos para situações mais específicas — use quando o instrutor indicar ou quando o problema pedir:

  • Debug — foco em investigar erros (logs, stack trace, hipóteses de causa). Analogia: médico do código analisando sintomas antes de receitar o remédio.
  • Multitask — várias frentes de trabalho em paralelo (subagentes ou tarefas simultâneas). Analogia: coordenar mini-equipes em tarefas que não dependem uma da outra no mesmo instante.

Combine o modo certo com o que você já configurou: allowlist, modelo (GPT, Claude, Gemini…) e janela de contexto — quanto mais arquivo e histórico no chat, mais “memória” o modelo consome de uma vez.

Rules são instruções persistentes — o “manual de estilo” do workspace. Ficam em .cursor/rules/ (arquivos .mdc). O agente consulta antes de agir, para você não repetir convenções em todo prompt.

No workspace modelo e no repositório clonado do curso você já tem exemplos (PRD, guidelines gerais, etc.). Abra pelo explorador: .cursor/rules/.

Always Apply vs Apply Intelligently

No Cursor, cada rule tem um tipo de aplicação (dropdown no topo do arquivo ou em Cursor Settings → Rules). Os dois modos que mais importam no curso:

Modo na UI O que faz Quando usar Custo de contexto
Always Apply
alwaysApply: true		 A rule entra em toda conversa (Ask, Plan, Agent), sem você pedir. Guardrails globais do workspace — ex.: idioma do código, estilo de commit, “não apagar sem avisar”. Alto — ocupa janela de contexto em todo prompt.
Apply Intelligently
alwaysApply: false + description		 O agente lê a descrição da rule e só inclui o texto completo quando julga relevante para a tarefa. Convenções de nicho (PRD, slides, SQL) que não precisam estar sempre na memória. Baixo na média — só paga o texto inteiro quando a rule é acionada.

Resumo: Always Apply = “sempre na mesa”. Apply Intelligently = “o agente decide se puxa esta rule conforme o que você pediu”. Uma description clara melhora muito o acerto no modo inteligente.

Há ainda Apply to Specific Files (globs) — a rule entra quando arquivos que batem o padrão estão no contexto (ex.: documents/prd-*.md). Não misture globs com Apply Intelligently na mesma rule se a intenção é só decisão do agente.

---
description: "PRD Template and Guidelines"
globs: "documents/prd-*.md"
alwaysApply: false
---

Combine rules com o que você já configurou no Bloco 01 (File deletion protection) — poucas rules em Always Apply, as essenciais.

Construindo o seu "Start My Day"

Fechar o dia com uma visão sistêmica: uma rotina repetível que combina métricas, gestão de tarefas e o que você já usou no curso.

Objetivo: Estruturar em modo Plan (ou Agent) um fluxo matinal que faça sentido para PM — inspirado em referências da comunidade Cursor.

Parte expositiva — Por que "Start My Day" 10 min

Pensar de forma sistêmica no trabalho matinal: em vez de abrir 10 abas manualmente, você cria um fluxo que busca métricas, status de tarefas e agenda — e monta um dashboard local ou interface atualizada.

Referência: exemplo do Ben Berube (Cursor) — pega tarefas do board, classifica por complexidade e elege um agente para trabalhar nas mais simples primeiro.

Para PMs: começar o dia atualizado em métricas, andamento de entregas, agenda e reuniões importantes.

Construção do Start My Day

No modo Plan, monte um arquivo .md que estruture os passos do seu SMD. Exemplo de ações:

  1. Atualizar dados de métricas (ex.: CSV local, API, Google Sheets via MCP)
  2. Pegar no Linear o status das tarefas e épicos prioritários
  3. Salvar artefatos (resumo local em Markdown ou JSON)
  4. Preparar build de interface (opcional: dashboard React/HTML com os dados consolidados)

Neste curso, o exercício deve consumir os arquivos de referência do ArenaCash no caminho learning/Cursor para PMs por Product Arena/case arenacash/ (especialmente dados-semanais-arenacash.csv, dados-quarter-q1.csv, atendimento-q1.csv e atendimento-resumo-semanal.csv).

O dashboard esperado pode ser simples, mas deve seguir o mesmo modelo da demo: coletar dados, montar um payload, renderizar HTML e abrir em localhost.
